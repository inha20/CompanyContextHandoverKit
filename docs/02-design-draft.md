## 1. 질문형 연구 질문

논문 개요의 RQ1~RQ4는 효과가 있다는 방향으로 읽힐 수 있어(예: RQ2는 환각이 줄어든다고 전제한다), 비교 대상과 측정이 드러나는 질문으로 다시 썼다. 선행에는 맥락 파일이 성공률을 높이지 못했다는 보고가 있으므로(S01) 효과가 있다고 가정하지 않는다.

## 2. 조건

### 2.1 기본 조건

'헤더'는 `build`가 팩 앞에 붙이는 세 문장이다(`src/companytoai/cli.py`의 `build_pack`). ① 이후 모든 답변은 이 문서를 기준으로 한다. ② 문서에 없는 내용은 추측하지 말고 '문서에 없음'이라고 답한 뒤 확인을 요청한다. ③ 문서 간 내용이 충돌하면 `updated` 날짜가 최신인 문서를 우선하고 충돌 사실을 알린다.

| 조건 | 정의 | 용도 |
|---|---|---|
| A | 맥락 없음. 질문만 준다 | 하한이다(D1). 회사 고유 사실은 모델이 알 수 없으므로 A와의 차이를 효과로 해석하지 않고 환각의 기준선으로만 쓴다 |
| B | C3과 같은 사실, 파일 이름, 갱신일, 지시 문장을 담되 구조 표지(`<document>` 태그, 제목, 표, 목록)를 없애고 줄글로 이은 것. 파일 이름과 갱신일은 문장 안에 풀어 쓴다 | Q1의 대조. 구조만 다르다(D2) |
| C0 (헤더 H0) | `build`의 `<document name updated>` 구조에서 헤더를 모두 빼고, 04번의 '불확실할 때의 행동' 절도 뺀 것 | Q2의 규칙 없음 |
| C1 (H1) | C0에 헤더 첫 문장을 더한 것 | Q2의 규칙 없음(기준 문장만) |
| C2 (H2) | C1에 모름 규칙(헤더 둘째 문장과 04번의 '불확실할 때의 행동' 절)을 더한 것 | Q2의 규칙 있음 |
| C3 (H3) | C2에 최신일 우선 문장(헤더 셋째 문장)을 더한 것. 현재 `build`의 출력과 같다 | 본 방법 |
| D-변동성 | C3에 점검과 갱신 루프를 더한 과정. 시뮬레이션한 시간의 흐름에서 `check`가 경고하면(현재 도구는 02·06번만, 기본 30일) 사람이 그 파일을 장부에 맞게 갱신한 것으로 본다 | Q3b. 개요의 조건 D |
| D-일률 | D-변동성과 같은 파일 갱신 횟수를 파일 구분 없이 같은 간격으로 나눠 쓴 것 | Q3b. 변동성 기반이라는 점만 뺀 대조 |

세 가지를 짚는다.

- **모름 규칙은 두 곳에 있다.** 헤더 둘째 문장과 예시 폴더의 04번 '불확실할 때의 행동' 절(문서에 없으면 추측하지 말고 05번의 담당 역할에게 확인하도록 안내한다)이 같은 취지다. 온보딩 프롬프트(`prompts/01_onboarding.md`)에도 있다(V: 파일 확인). 한 곳만 빼면 규칙의 효과를 작게 잴 수 있어(AI의 추론) C0과 C1은 헤더 문장과 04번의 해당 절을 함께 뺀다. 이 조작이 규칙 없음과 있음의 차이를 정의한다.
- **B는 정보량을 C3과 같게 한다.** 갱신일과 파일 이름을 빼면 B는 낡음, 충돌, 근거 인용 문항에서 정보를 덜 갖게 되어 구조가 아니라 정보의 차이를 재게 된다(D2). 대신 구조 표지를 없애는 변환 규칙이 결과에 영향을 주므로 규칙을 미리 고정하고 공개해야 한다(§8, O3).
- **D는 상한이다.** 사람이 경고를 놓치지 않고 파일을 장부에 맞게 완전히 고친다고 가정하므로 D-변동성의 효과는 상한이다. 사람이 일부만 고치는 경우는 이 설계에 없다(§8).

C0⊂C1⊂C2⊂C3은 헤더 문장을 하나씩 더하는 소거 사슬이다.

### 2.2 고정하는 것

- 컨텍스트 팩을 먼저 두고 업무 지시([prompts/02_task_with_context.md](../prompts/02_task_with_context.md) 형식, `근거:`와 `가정:` 줄 포함)를 뒤에 둔다. 헤더가 문서 앞에 있고 질문이 뒤에 있는 배치다. 공식 문서(S12)는 긴 문서를 앞에 두고 질문을 맨 끝에 두라고 권한다.
- 갱신 과제(T4)는 [prompts/03_handover_update.md](../prompts/03_handover_update.md)의 형식을 쓴다.
- 온도, 최대 출력 길이, 반복 횟수 k는 모든 조건에서 같게 한다. 값은 모델 호출 수단이 정해진 뒤 정한다.
- 한 번에 질문 하나를 새 대화에서 묻는다(단일 턴). 온보딩 프롬프트의 이해 확인과 공백 보고는 시험하지 않는다(§8).
- **두 지시가 부딪힌다.** `prompts/02`는 문서에 없어서 가정한 내용을 `가정:`으로 표시하게 하고, 헤더는 추측하지 말고 '문서에 없음'이라고 답하라고 한다(V: 파일 확인). 이 설계는 둘을 그대로 두고, M4에서 `가정:`으로 표시된 추측을 근거 없는 확정 답과 따로 센다.

## 3. 시나리오와 정답

### 3.1 장부 방식

가상 회사마다 **장부**를 만든다. 장부는 사실의 목록이며 각 사실에 값, 효력이 생긴 날, 그 사실이 쓰이는 파일과 항목이 붙는다. 사실이 바뀐 기록(변경 기록)도 장부에 둔다. 폴더는 장부에 갱신 규칙을 적용해 파일별 내용과 `updated`를 그려 낸 것이다. **정답은 폴더가 아니라 장부의 평가일 값에서 뽑는다.** 변경 기록 장부에서 정답을 뽑는 ChurnBench(S32)의 방식을 가져온 것이다(D7).

파일의 `updated`는 그 파일 안의 어떤 사실이든 마지막으로 반영된 날이다. 파일이 다른 이유로 고쳐졌으면 그 안의 낡은 문장은 새 `updated`를 달고 남는다. 폴더 상태 F3이 이 경우다.

**폴더 상태 만들기.** 같은 장부에서도 폴더가 얼마나 낡았는지는 갱신 규칙이 정한다. 규칙은 둘이다.

- (가) 지연 규칙: 사실이 바뀐 뒤 파일에 반영되기까지의 지연이다. 파일의 변동성 등급마다 분포를 정하고, 끝내 반영되지 않는 경우도 둔다.
- (나) 점검 규칙(조건 D): 시뮬레이션한 시간의 흐름에서 `check`가 경고하면 그 시점에 그 파일을 장부에 맞게 갱신한다.

F0~F3은 (가)를 문항마다 직접 지정해 만든 통제 상태이고, Q3b는 변경 이벤트를 시간순으로 재생하며 (가)와 (나)가 만드는 상태를 쓴다. (가)의 값은 이 검색에서 근거를 얻지 못했다. S03이 맥락 파일의 갱신이 짧은 기간에 몰린다고 보고했으나 소프트웨어 저장소 대상이고 반영 지연의 분포는 아니다. 값은 사람이 정해야 하며(O9), 하나의 값을 대표로 주장하지 않고 여러 값으로 민감도를 보자는 것이 AI의 제안이다.

| 필드 | 뜻 |
|---|---|
| id, company | 문항 번호, 가상 회사 번호 |
| eval_date | 평가일(장부의 시점) |
| type | T1~T4(§3.2) |
| question | 질문 또는 세션 로그 |
| gold | 정답 값, 검사할 제약 목록, 거절 여부와 안내 대상, 정답 변경 집합 중 하나 |
| gold_source | 정답이 있는 파일과 장부 항목 |
| folder_state | F0~F3 또는 시간선 번호(Q3b) |
| update_policy | 지연 규칙과 점검 규칙의 값 |

### 3.2 문항 유형과 폴더 상태

문항은 무엇을 묻는지(유형)와 폴더를 어떻게 그렸는지(상태)의 조합이다.

| 유형 | 묻는 것 | 정답 |
|---|---|---|
| T1 조회 | 폴더에 있는 현재 사실 | 장부의 평가일 값 |
| T2 규칙 | 04번 규칙이 응답을 제약하는 작성 과제 | 검사할 제약 목록 |
| T3 답 없음 | 장부에 없는 사실 | 거절과 확인 대상 안내 |
| T4 갱신 | 세션 로그를 주고 쓰게 하는 변경안 | 장부 변경에서 나온 변경 집합 |

| 상태 | 이름 | 뜻 |
|---|---|---|
| F0 | 최신 | 모든 파일이 장부와 같다 |
| F1 | 낡음만 | 관련 사실이 한 파일에서 장부보다 낡았고 바로잡는 진술이 폴더에 없다 |
| F2 | 충돌, 날짜 일치 | 낡은 값의 파일은 `updated`가 더 오래되고, 최신 값의 파일은 더 새롭다 |
| F3 | 충돌, 날짜 어긋남 | 낡은 값의 파일이 다른 이유로 고쳐져 `updated`가 최신 값의 파일보다 새롭다 |

F1은 낡은 값만 폴더에 있어 폴더만으로는 정답을 알 수 없다. 이때의 적절한 응답은 값을 말하되 파일이 낡았을 수 있다고 알리는 것이다(AI의 정의, M6).

### 3.3 예시

예시는 이 저장소의 가상 예시 폴더(`examples/acme_handover`, 가상 회사 '에이크미 푸드테크')에서 가져왔다. '주입'은 설명을 위해 폴더를 고쳐 만든 가정이며 예시 파일의 내용이 아니다. 예시 파일은 바꾸지 않았다.

### 3.4 크기와 정밀도

논문 개요는 가상 기업 2개(제조와 서비스 각 1개)와 시나리오 40~60개를 말한다. 저장소에 있는 예시는 서비스(SaaS) 회사 1개이고 제조 회사는 없다. 이 초안은 '시나리오'를 (질문, 폴더 상태) 쌍인 문항 하나로 읽었다(AI의 해석). 칸은 T1×F0~F3, T2, T3, T4의 7개이고 회사가 2개면 14칸이므로 40~60문항은 칸당 3~4개다(40÷14≈2.9, 60÷14≈4.3). 칸 단위의 결론은 낼 수 없다.

한 조건의 정답률에 대한 95% 반폭은 정규 근사에서 최악의 경우(p=0.5) 문항 수가 15개이면 25.3점, 30개이면 17.9점, 50개이면 13.9점, 100개이면 9.8점, 200개이면 6.9점이다(산술이며 문헌 근거가 아니다. 저장소에 코드는 없다).

같은 장부에서 나온 문항은 서로 독립이 아니다. 효과적인 표본 크기를 정하는 것은 문항 수보다 장부의 수이고, 회사가 2개뿐이면 회사 사이의 변동을 추정할 수 없어 '회사 일반'으로 넓힐 수 없다(AI의 추론). 장부의 수를 늘리려면 변경일과 값을 바꿔 가며 장부를 여러 개 만든다. 문항 수는 O4다.

### 3.5 가상 데이터만 쓴다

실제 회사의 자료와 개인정보는 쓰지 않는다. 이 저장소의 보안 주의(영업비밀과 개인정보는 공개 저장소에 올리지 않는다)와 같은 이유다.

## 5. 분석 계획

- 모든 비교는 문항 짝이다(같은 문항, 조건이나 폴더 상태만 다르다).
- 미리 정한 대조는 아래 6개이고 대조마다 주 지표를 미리 정한다.

| 대조 | 비교 | 주 지표 | 질문 |
|---|---|---|---|
| K1 | C3 − B | M1(M2, M3, M9는 보조) | Q1 |
| K2 | C2 − C1 | M4와 M5를 함께(한쪽만 보면 거절을 늘리는 대가를 놓친다) | Q2 |
| K3 | C3에서 F0 − F1, F0 − F2, F0 − F3 | M1(M6은 보조) | Q3a |
| K4 | (가) D-변동성 − C3, (나) D-변동성 − D-일률. 시간선 위에서 | M6 | Q3b |
| K5 | C3 − C2를 F2와 F3으로 나눠서 | M7 | Q3c |
| K6 | (가) 갱신안 − 정답 변경 집합, (나) 갱신안 − 사람이 같은 로그로 만든 갱신(사람 갱신도 같은 정답에 채점해 같은 지표로 비교) | M10(M11, M12는 보조) | Q4 |

- 보고는 차이와 95% 신뢰구간이며, 문항을 장부 단위로 묶은 부트스트랩을 쓴다. 이진 결과는 McNemar 검정을 보조로 쓴다.
- 모델별로 따로 보고하고 합치지 않는다(C16).
- 대조 6개 밖의 비교는 탐색적이라고 표시한다. 다중 비교 보정은 하지 않는다(AI의 선택이며 사람이 바꿀 수 있다).
- 판정자와 사람의 일치는 표본에서 Cohen의 kappa로 잰다. 판정자와 후보의 모델 계열을 나누고, 응답 위치를 바꿔 평균한다(S46, S47, D11).
- 동결하지 않는다.

## 6. 막힌 실험의 기록

- **상태:** 조건 A~D 어느 것도 실행하지 않았다. 시나리오 파일, 평가 스크립트, 예비 실험이 없다.
- **막힌 이유:** 모델을 호출하고 결과를 평가할 방법이 없다(사용자 답변, 2026-11-08).
- **풀리는 조건:** (1) 모델 계열 2개 이상을 호출하고 결과를 돌려받을 수단, (2) 판정 표본을 보는 사람 평가자 2명 이상과 Q4에서 사람 갱신을 만들 사람, (3) §7의 열린 항목.
- **규모 감각:** 호출 수의 상한은 문항 수 × 조건 수 × 모델 수 × 반복 수다. 예를 들어 180 × 8 × 2 × 3 = 8,640회이고 판정 호출은 별도다. §2.3처럼 질문별로 필요한 조건만 돌리면 이 곱의 일부이므로 상한이다(산술).
- **모델 호출 없이 할 수 있는 것:** 장부에서 폴더, 문항, 정답을 만드는 코드. 결정적이어서 단위 시험이 가능하다. 아직 만들지 않았다(O7).

## 8. 한계와 위험

- 가상 회사와 가상 장부이므로 실제 회사의 지저분함(서로 어긋나는 메모, 비공식 용어, 오탈자, 형식이 섞인 표)을 담지 못한다.
- 문항을 LLM으로 만들면 같은 계열 모델이 답할 때 사전 지식이 겹칠 수 있다. 문항은 장부에서 규칙으로 만들고 사람이 표본을 검토한다(AI의 제안).
- 문항과 폴더를 공개하면 이후 모델의 학습 자료에 들어갈 수 있다. 생성기를 공개하고 문항은 시드로 새로 만드는 방식이 대안이다(AI의 제안).
- 판정자의 편향(S46: 위치, 장황함, 자기 선호)이 있다. 판정자와 후보의 모델 계열을 나눈다.
- B를 만드는 규칙이 결과에 영향을 준다. 표와 목록을 줄글로 바꾸는 방식에 따라 B가 일부러 나쁘게 만들어졌다는 의심을 살 수 있어 변환을 결정적으로 고정한다(O3).
- 단일 턴 설계다. 실제 사용은 온보딩 후 여러 턴이고 온보딩 프롬프트의 이해 확인과 공백 보고가 있으나, 이 설계는 팩과 질문 하나를 새 대화에서 준다. 온보딩 효과는 시험하지 않는다.
- 헤더의 모름 규칙과 `prompts/02`의 `가정:` 지시가 부딪힐 수 있어(§2.2) 결과 해석에서 `가정:`으로 표시한 추측을 따로 다뤄야 한다.
- 조건 D는 사람이 완벽히 갱신한다고 가정해 효과의 상한이다. 갱신 지연의 분포는 근거 없이 정한 값이다(O9).
- 세션 로그(T4)를 만드는 방식(템플릿 대 LLM 생성)이 재현성과 현실성 사이에서 갈린다. 템플릿은 재현되지만 실제 대화와 다르다.
- `updated:` 날짜는 파일 단위라 파일 안의 문장 단위 낡음을 알려 주지 못한다(C10).
- 폴더와 프롬프트가 한국어이므로 영어 문헌의 결과가 그대로 옮겨진다는 보장이 없다.
- 헤더 문장이 한국어 세 문장으로 고정되어 있어 문구에 대한 민감성(S17)은 따로 시험하지 않는다.
- 이 설계는 결과를 예측하지 않는다.
